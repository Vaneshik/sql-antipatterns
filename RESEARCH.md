# SQL-антипаттерны: определение, каталог и границы ВКР

Обзор на 20 октября 2026 года. Сейчас предмет работы — логический план запроса
Apache Calcite (`RelNode`). Синтаксический и гибридный анализ отложены.

## Что считать антипаттерном

**Антипаттерн — повторяющийся способ решения задачи, который при определённых
условиях создаёт нежелательные последствия.** Он может выглядеть разумно
и давать правильный результат, но усложнять сопровождение, создавать риск ошибки
или лишнюю работу.

Основа определения — [введение Karwin, раздел 1.2][karwin-intro],
[глава 1 предоставленного русского издания, с. 23–25](BOOK_NOTES.md#chapter-1)
и [SQLCheck, разделы 1–2][sqlcheck]. Karwin отдельно разбирает законные применения:
контекст входит в описание антипаттерна. `JOIN`, `DISTINCT` или подзапрос сами
по себе не являются проблемой.

Для этой ВКР рабочее определение уже: **антипаттерн запроса — повторяемая
конструкция, для которой можно указать условия обнаружения в логическом плане,
объяснить нежелательное последствие и предложить обоснованную рекомендацию.**
Требование рекомендации — условие нашего каталога, а не универсальная часть
всех определений термина.

| Понятие | Как использовать в работе |
|---|---|
| Подозрительный признак, smell | Повод проверить запрос. По [Fowler][smell], сам признак ещё не доказывает проблему. |
| Антипаттерн | Повторяемый приём с объяснимым недостатком в заданном контексте. |
| Ошибка, bug | Нарушение требуемого результата или контракта. Может одновременно быть проявлением антипаттерна. |
| Возможность преобразования | Есть другой эквивалентный способ записать запрос. Это ещё не доказательство недостатка исходного варианта. |
| Выигрыш в производительности | Измеренный эффект на определённой СУБД, данных и настройках. Из структуры `RelNode` он не следует. |

Последние различия — рабочие договорённости проекта. Они не образуют
взаимоисключающую общепринятую классификацию.

## Какие бывают SQL-антипаттерны

В [Karwin 2010/2022][karwin1] выделены проектирование схемы, физическое устройство,
запросы и код приложения. [SQLCheck][sqlcheck] дополнительно выделяет проблемы
данных, а [DeFiHap][defihap] — конфигурации Hive.
Ниже — сводная классификация для обзора, а не дословное оглавление одной работы.

| Где возникает проблема | Примеры | Что нужно для проверки |
|---|---|---|
| Модель данных | Список значений в одной колонке (Jaywalking), EAV, полиморфные связи, отсутствие ограничений целостности | Схема, ограничения и требования предметной области; иногда несколько запросов |
| Физическое устройство и настройки | Неудачный набор индексов, типы данных, параметры выполнения Hive | Каталог СУБД, статистика, настройки и нагрузка |
| Логика отдельного запроса | Сравнения с `NULL`, нежелательное размножение строк, избыточные операции, потеря свойств внешнего соединения | Логический план, выражения, типы и ограничения схемы |
| Данные | Несогласованные значения, выбросы, отсутствие ожидаемой целостности | Профилирование содержимого БД |
| Работа приложения с БД | N+1, SQL injection, ошибки границ транзакций | Код приложения, происхождение параметров и последовательность обращений |
| Исходная запись SQL | `SELECT *` как способ записи, неоднозначный стиль, форматирование | Исходный текст или синтаксическое дерево; не текущий этап ВКР |

«Логическое проектирование БД» в книгах — устройство таблиц и связей.
«Логический план запроса» в этой работе — дерево операций над данными.
Эти понятия нельзя подменять друг другом.

Есть и независимая ось: **последствия** — корректность, производительность,
сопровождаемость, переносимость или безопасность. Один случай может затрагивать
несколько последствий. Общий `severity` без объяснения этих различий мало полезен.

## Что видно в логическом плане

Для каталога разделяю четыре уровня информации:

1. **Логический план:** `Join`, `Project`, `Aggregate`, `Filter`, выражения и связи колонок.
2. **Схема и семантика:** типы, `NULL`, PK/UNIQUE/FK, свойства функций. Они нужны многим логическим правилам.
3. **Физическое выполнение:** индексы, статистика, выбранные алгоритмы, материализация, настройки СУБД.
4. **Измерения:** реально обработанные строки, обращения к буферам и время.

Текущая задача — первые два уровня. Третий и четвёртый нужны для отдельной
оценки пользы. Метаданные схемы не превращают логический анализ в физический.
Применимость правила Calcite сама по себе не доказывает наличие антипаттерна.

## Кандидаты в каталог

Это предлагаемые условия для исследования, собранные из источников и семантики SQL.
Таблица не утверждает, что все случаи уже реализованы в прототипе или являются
ошибкой при любом применении.

| Конструкция | Когда есть основание для рекомендации | Контрпример или ограничение | Информация / источник |
|---|---|---|---|
| **DISTINCT после JOIN для проверки существования** | Выводятся только колонки левого входа с его ключом; INNER JOIN может размножить их. Рассмотреть semi join / EXISTS. | Без ключа слева замена может сохранить лишние одинаковые строки. Уникальность ключа соединения справа исключает размножение. | План + ключи; [SQLCheck, Table 1][sqlcheck-table] |
| **DISTINCT над уже уникальным результатом** | Уникальность выводимых значений доказана для текущего входа операции. | PK базовой таблицы может повторяться после JOIN. Обычный nullable UNIQUE допускает повторные NULL, которые DISTINCT схлопывает. | План + ограничения; [PostgreSQL constraints][pg-constraints] |
| **DISTINCT в простом IN/EXISTS** | Число одинаковых строк не влияет на membership или наличие строки. Рассматривать ограниченный подзапрос без LIMIT/FETCH и OFFSET, сложных агрегаций и побочных эффектов. | Для значений `1, 1, 2` запрос `SELECT DISTINCT x ORDER BY x LIMIT 2` даёт `1, 2`, без DISTINCT — `1, 1`; проверка `2 IN (...)` меняется. Не заменять NULL-aware NOT IN обычным anti join. | План + свойства выражений; [PostgreSQL subqueries][pg-subqueries], [порядок SELECT][pg-select] |
| **Filter по ключу группировки над Aggregate** | Детерминированный предикат зависит только от обычных ключей непустого GROUP BY; его можно перенести ниже агрегации. | Предикат по COUNT/SUM, GROUPING SETS и volatile-функции требуют другой семантики. СУБД может уже выполнить перенос. | План + свойства выражений; [SQLCheck HAVING][sqlcheck-having], [PG planner][pg-planner] |
| **LEFT JOIN с отбрасывающим NULL фильтром справа** | Например, `WHERE r.status = 'paid'` исключает добавленные соединением строки. Можно выразить INNER JOIN. | `r.id IS NULL` — обычная проверка отсутствия совпадения. Перенос WHERE в ON меняет результат. Намерение автора неизвестно. | План + трёхзначная логика; [PostgreSQL joins][pg-joins] |
| **Декартово произведение** | После учёта окружающих фильтров нет условия, связывающего входы. Можно предупредить о всех комбинациях строк. | «Товары × даты» может быть задачей запроса. `Join(TRUE)` не достаточен для диагноза: связь бывает в Filter выше. | План; размер результата требует данных/статистики; [PostgreSQL joins][pg-joins] |
| **Неиспользуемая правая сторона LEFT JOIN** | Правые значения дальше не используются и доказано не более одного совпадения. Соединение можно удалить. | Без уникальности справа соединение меняет число копий. INNER JOIN дополнительно требует доказать наличие соответствия. | План + ключи, для INNER также FK/NOT NULL; [WeTune, Table 7][wetune], [SQLFluff ST11][sqlfluff-structure] |
| **DISTINCT вместе с GROUP BY** | После группировки вывод уже гарантированно уникален, например сохранены все ключи группы. | `SELECT DISTINCT COUNT(*) ... GROUP BY customer_id`: размеры разных групп могут совпадать, DISTINCT нужен. | План + уникальность; [SQLFluff AM01][sqlfluff-ambiguous], [PostgreSQL DISTINCT][pg-distinct] |
| **NOT IN при возможном NULL** | Можно показать риск UNKNOWN вместо ожидаемого TRUE, если nullable-путь действительно существует. | Поведение бывает намеренным. NOT EXISTS не эквивалентен механически; важны NULL слева и пустой подзапрос. | План + nullability; [PostgreSQL NOT IN][pg-not-in] |
| **Сравнение `col = NULL`** | Для обычного SQL-сравнения результат UNKNOWN; для проверки пропуска нужен IS NULL. | Нельзя угадывать намерение автора. Nullable `col = col` тоже не безусловная тавтология. | Выражения + типы; [PostgreSQL comparisons][pg-comparisons] |
| **UNION вместо UNION ALL** | Для удаления дедупликации доказано отсутствие повторов внутри каждого входа и пересечений между входами. | Одной непересекаемости входов недостаточно. Устранение повторов может быть целью UNION. | План + ограничения/предикаты; [PostgreSQL set operations][pg-union] |
| **Функция или CAST над колонкой в фильтре** | Форма выражения — повод проверить доступ по обычному индексу. | Индекс на выражении может полностью подходить; CAST, timezone и collation важны для результата. | План показывает кандидата; оценка затрат требует физического контекста; [PostgreSQL expression indexes][pg-expression-index] |
| **Повторные коррелированные подзапросы** | Повторяющиеся поддеревья дают повод проверить повторное вычисление. | Индексный lookup может быть выгоден. Scalar subquery при нуле строк даёт NULL, при нескольких — ошибку; простой JOIN это не сохраняет. | План + семантика, затем физический план/измерения; [PostgreSQL scalar subqueries][pg-scalar] |
| **Повторные обращения к CTE** | Нужно выяснить, повторяется вычисление или используется материализация. | PostgreSQL может вычислять CTE один раз; поведение зависит от MATERIALIZED/NOT MATERIALIZED. Само повторение имени ничего не доказывает. | Исходная структура и физический контекст; [PostgreSQL CTE][pg-cte], [BigQuery catalog][bigquery] |

В первых трёх строках устранение дубликатов означает обычный DISTINCT,
а не PostgreSQL DISTINCT ON. Во всех предполагаемых преобразованиях сохраняются
условия фильтрации и мультимножество результата — число копий строк тоже важно.

## Почему каталоги нельзя копировать механически

- **BigQuery:** правило 2 предлагает добавить DISTINCT внутрь IN. Это контекстная рекомендация конкретного движка, а не опровержение семантической избыточности дубликатов для membership. Переносить её или противоположный совет в PostgreSQL без проверки нельзя. [Каталог][bigquery].
- **SQLFluff:** ST08 относится к скобкам около DISTINCT, ST11 не делает автоматический fix для неиспользуемого outer join. Совпадение названий правил не означает совпадение условий. [Structure rules][sqlfluff-structure].
- **SQLCheck:** `DISTINCT and JOIN` уже есть в Table 1 статьи. Это известный случай, не новое правило нашей ВКР. Одноимённый C++ CLI не следует отождествлять с Python-системой из статьи. [Статья][sqlcheck], [C++-каталог][sqlcheck-cli].
- **Flink:** PLAN_ADVICE анализирует оптимизированный физический FlinkRelNode и учитывает особенности Flink. Это уже существующий пример рекомендаций по узлам плана; его каталог не совпадает с нашими логическими правилами. [PlanAnalyzer][flink].
- **PostgreSQL:** оптимизатор уже упрощает подходящие EXISTS и переносит безопасные HAVING. Наличие конструкции в плане Calcite не доказывает, что PostgreSQL исполнит лишнюю операцию. [subselect.c][pg-exists-source], [planner.c][pg-planner].
- **Sabadosh/Kotsovsky:** опубликованный `_detect_redundant_distinct` проверяет DISTINCT вместе с GROUP BY. Он не проверяет наш JOIN-сценарий; условие «есть GROUP BY» само по себе недостаточно для удаления DISTINCT. [Исходник][sabadosh-code].

## Небольшой каталог для первого этапа

Предлагаю начать с трёх правил:

1. **DISTINCT + JOIN → EXISTS.** Уже есть ограниченный детектор; формализовать его условия и контрпримеры.
2. **DISTINCT над доказанно уникальным входом.** Проверяет, как ключи и операции плана влияют на уникальность.
3. **Фильтр по ключам группировки.** Проверяет зависимости выражений и условия допустимого переноса.

Это выбор по объёму реализации и проверяемости условий, а не вывод о новизне.
Если нужны три менее похожих семейства, второе можно заменить на
`Filter` над `LEFT JOIN`, отвергающий NULL справа. Окончательный каталог согласовать
с руководителем; остальные строки пока остаются кандидатами.

Для каждого правила фиксировать: задачу пользователя, форму плана, необходимые
метаданные, причину замечания, рекомендацию, условия корректности, допустимые случаи,
положительные/отрицательные примеры и источник.
Если существенных данных не хватает, результат — «недостаточно сведений»,
а не подтверждённая проблема. Это требование к будущему каталогу; отдельного такого
статуса в текущем CLI ещё нет.

## Что уже есть и как проверять дальше

В [Analyzer.java](src/main/java/io/github/vaneshik/sqlantipatterns/Analyzer.java)
реализован только первый ограниченный случай. Схема двух таблиц задана в коде.
Основная проверка идёт по `RelNode`, исходный `SqlNode` используется для границ
правила. Это не отдельный синтаксический детектор.

При конвертации включён `aggregateUnique`: иначе Calcite может убрать
проверяемый DISTINCT до диагностики. Вообще нормализация способна стереть исходную
конструкцию; этап анализа и настройки конвертации нужно фиксировать в экспериментах.

[Исходный пример](examples/distinct-join.sql), [ручной вариант с EXISTS](examples/exists.sql)
и [контрпример без ключа](examples/without-key.sql) показывают разные исходы.
Тесты проверяют детектор, не доказывают общую эквивалентность SQL и ускорение.
Автоматическое переписывание, PostgreSQL-эксперименты и интеграция DBeaver ещё не сделаны.

Ближайшая работа:

- Зафиксировать условия трёх выбранных правил и собрать размеченные примеры с дубликатами, NULL и границами применимости.
- Оценивать ложные срабатывания, пропуски и неподдержанные случаи раздельно. Варианты одного исходного запроса не считать независимыми наблюдениями.
- Для допустимых исправлений сравнить мультимножества результатов на PostgreSQL. Отдельно сравнивать планы и время на одинаковых данных, индексах и настройках.
- Регистрировать отсутствие выигрыша и регрессии. Различать факт обнаружения, корректность рекомендации и измеренную пользу.

С руководителем обсудить определение антипаттерна, состав первого каталога
и достаточный исследовательский вклад. Само применение RelNode уже имеет аналоги.
