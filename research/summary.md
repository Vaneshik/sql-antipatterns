# SQL-антипаттерны: краткий обзор

ВКР: разработка расширения для DBeaver, которое анализирует логический план SQL-запроса (`RelNode`), находит антипаттерны и предлагает исправления.

Сейчас работаю с логической частью: условия обнаружения, объяснение проблемы
и корректность рекомендации. Синтаксический анализ антипаттернов — возможное продолжение.

## Что такое антипаттерн

**Антипаттерн — повторяющийся способ решения задачи, который в определённых
условиях приводит к нежелательным последствиям.** Например, запрос возвращает
нужные данные, но создаёт лишние промежуточные строки или скрывает ошибку в соединении.
Такое понимание опирается на [Karwin](https://media.pragprog.com/titles/bksqla/introduction.pdf)
и [SQLCheck](https://arxiv.org/html/2004.10232).

Для каждого случая нужны условия, объяснение и допустимая альтернатива.
Одного наличия `JOIN`, `DISTINCT` или подзапроса недостаточно.
Подозрительная конструкция — повод проверить запрос; ускорение после исправления
нужно измерять отдельно.

## Какие бывают

| Область | Примеры | Что нужно анализировать |
|---|---|---|
| Схема данных | Списки в одной колонке, полиморфные связи, отсутствие ограничений | Таблицы, связи и требования задачи |
| Физическое устройство и настройки | Неудачные индексы, параметры выполнения | Индексы, статистика и нагрузка |
| Отдельный запрос | Лишняя дедупликация, нежелательное размножение строк, ловушки NULL | Логический план, типы и ключи |
| Данные | Несогласованные значения и нарушения ожидаемой целостности | Содержимое БД |
| Приложение | N+1, SQL injection, ошибки работы с транзакциями | Код и последовательность запросов |
| Запись SQL | Стиль, неоднозначные конструкции, SELECT * как исходная запись | Текст или синтаксическое дерево |

Это сводка классификаций [Karwin](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/),
[SQLCheck](https://arxiv.org/html/2004.10232#S2.T1) и [DeFiHap](https://www.vldb.org/pvldb/vol14/p2671-mao.pdf).
В этой ВКР фокус — **отдельный запрос**. Логический план показывает операции над
данными; для выводов о корректности часто нужны ещё PK/UNIQUE, типы и допустимость NULL.
Логическое проектирование схемы и логический план запроса — разные вещи.

## Пример: DISTINCT после JOIN

Нужно получить клиентов с оплаченными заказами:

```sql
SELECT DISTINCT c.id, c.name
FROM customer c
JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid';
```

Если у клиента несколько подходящих заказов, JOIN размножает его строки,
затем DISTINCT убирает копии. Проверку наличия заказа можно выразить через EXISTS:

```sql
SELECT c.id, c.name
FROM customer c
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.id AND o.status = 'paid'
);
```

Здесь `c.id` — первичный ключ. Если выводить только `c.name`, замена может изменить
результат: два клиента с одинаковым именем дадут две строки вместо одной.
Конструкция DISTINCT + JOIN уже есть в каталоге [SQLCheck, Table 1](https://arxiv.org/html/2004.10232#S2.T1).
Интерес для ВКР — в проверяемых условиях диагностики и оценке пользы рекомендации.

## Что брать в первый каталог

| Правило | Что требуется проверить | Статус |
|---|---|---|
| DISTINCT + JOIN → EXISTS | Уникальность левого результата, возможность размножения, использование правых колонок | Есть ограниченный прототип |
| DISTINCT над уже уникальным входом | Уникальность после всех предшествующих операций, а не только PK исходной таблицы | Кандидат |
| Фильтр по ключу группировки | Зависимости предиката и допустимость переноса ниже Aggregate | Кандидат |

В [подробном обзоре](README.md) — 14 кандидатов, необходимые сведения,
контрпримеры и границы источников. Там же разобраны NOT IN с NULL,
внешние соединения, декартовы произведения, функции в предикатах и другие случаи.

Дальше: согласовать каталог, собрать размеченные примеры, измерить ложные
срабатывания и пропуски. Для исправлений отдельно проверить результаты и время
на PostgreSQL. Автоматического rewrite и интеграции с DBeaver пока нет.

## С чего читать

1. **[Karwin, введение к SQL Antipatterns, 2010](https://media.pragprog.com/titles/bksqla/introduction.pdf)** — короткое определение, устройство описания и законные применения антипаттернов.
2. **[SQL Antipatterns, Volume 1, 2022](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/)** — основной книжный каталог. **[More SQL Antipatterns, 2026](https://pragprog.com/titles/bksap2/more-sql-antipatterns/)** — продолжение про JOIN, индексы, пагинацию, N+1 и другие темы.
3. **[SQLCheck, SIGMOD 2020](https://arxiv.org/html/2004.10232)** — научная работа об обнаружении, диагностике и исправлении; учитывает запросы, схему и данные.
4. **[DeFiHap, PVLDB 2021](https://www.vldb.org/pvldb/vol14/p2671-mao.pdf)** — анализатор HiveQL; показывает зависимость рекомендаций от движка и настроек.
5. **[WeTune, SIGMOD 2022](https://ipads.se.sjtu.edu.cn/_media/publications/wetune_final.pdf)** — преобразования логических планов с явными условиями корректности.
6. **[PostgreSQL: подзапросы и NULL](https://www.postgresql.org/docs/18/functions-subquery.html)** и **[JOIN, WHERE, GROUP BY](https://www.postgresql.org/docs/18/queries-table-expressions.html)** — семантика, по которой проверять рекомендации.
